    Migrate from PRemoteM

    PRemoteM vs 1Remote

    1Remote is the upgraded version of PRemoteM.

    Since PRemoteM is our old name, our migration tool will auto detect your old data when you first start 1Remote.

    If you miss the auto-migration, you can still import it manually:

    1. Find the PRemoteM database file PRemoteM.db. It is in %AppData%\PRemoteM\, or next to PRemoteM.exe if you ran PRemoteM in portable mode.
    2. In 1Remote click the + button in the upper-right corner, then click Import and choose import PRemoteM db. Select the PRemoteM.db file and click "Open".

    Warning

    If you had turned on PRemoteM's RSA database encryption, 1Remote can no longer decrypt that database (support for it was removed in 1Remote 1.3.0). Disable the encryption in PRemoteM before you import the database, otherwise the names, addresses and passwords are imported encrypted and unreadable.

    Overview

    Managing Servers

    Adding Server

    1. Click the + button in the upper-right corner of the main window.

    2. Choose a protocol, such as RDP, SSH, or VNC, at the top of the pop-up window.

    3. Set the server's name, tags, notes (supports Markdown), and others.

    4. (Optional) Change the server icon (pick one or upload your own) and give the server a color, see Highlight a server.

    5. (Optional) Configure scripts for the server, such as opening VPN before starting remote desktop, or closing VPN after closing remote desktop. Scripts support cmd, PowerShell, and Python. Please see the Open a VPN before connect for further details.

    6. Continue entering server address, port, credentials and other information, and select your desired connection settings.

    7. Click the Save button to complete adding the server and return to the main window.

    View: cards, list or tree

    Click the ☰ menu button in the upper-right corner of the main window and choose View. The servers of the main window are shown in one of three ways:

    • Card: one card per server, with the icon, the name and the tags.
    • List: one row per server. Drag the edge of a column header to change its width, and click a column header to sort by it.
    • Tree: the servers in a tree of folders that you create yourself. Every database you connected (every data source, see Use online database) is a root of the tree. Right-click a node and choose Create a folder, then drag servers into the folder. Right-click a folder to Rename or Delete it (the servers inside move up to the parent folder). Tags in the tag bar of this view can be **Pin**ned, so the bar keeps showing them when the list is filtered.

    Sorting

    • In list mode, click on the header above the list to sort the servers.
    • Or click the ☰ menu button in the upper-right corner of the interface and choose Sorting: Sort by drag (drag each server to its place), by protocol, by name or by host name. Host names are sorted naturally, so 192.168.1.9 comes before 192.168.1.10.

    Edit

    When you move the mouse over a server, a Settings button appears. Click it for a menu where you can connect, edit, duplicate, delete the server, or copy its address, user name and password. (Note: If you connect to a database with a read-only account, you will not be able to edit, copy the credentials or delete server information stored in that database. Such databases carry the addition (Readonly) in the database list of Options -> Database, see Online database.)

    Tip

    You can also directly enter the edit interface by right-clicking on a server with your mouse.

    Select several servers

    Tick the check box of a server to select it, or hold Ctrl / Shift and click servers as you do in Windows Explorer. With several servers selected, the buttons at the bottom of the main window act on all of them: Connect, Edit, Delete, Export and Create desktop shortcut.

    Bulk edit

    Click the Edit button at the bottom of the main window with several servers selected to enter the batch editing interface, where you can change the address, the credentials, the tags and so on for all of them at once. With tags, you can select all servers with one tag and change their addresses or passwords in one go.

    Data export

    Warning

    The exported data is stored in plain text, so please handle it with care.

    When some servers are selected, the Export button exports them to a json file which you can import on another PC or simply keep as a backup. The file name is the date and time of the export, for example 20261123103000.json. If you turned on secondary verification, you have to verify yourself before the export starts. Please see the Data synchronization for further details.

    Data import

    Click the + button in the upper-right corner of the main window, then Import. You can import:

    Importing from 1Remote

    Choose import json and select a json file exported by 1Remote.

    Importing from mRemoteNG

    1. In mRemoteNG, right-click on the server and choose "Export to File...". Set the "File Format" to "mRemoteNG CSV" in the pop-up window, and click the OK button in the lower-right corner to export.
    2. In 1Remote, choose "import mRemoteNG csv". Select the CSV file you just exported in the pop-up dialog, and click "Open" to complete the import.

    Importing from PRemoteM

    Since PRemoteM is our old name, you can also import data from PRemoteM.

    Our migration tool will auto detect your old data when you first start 1Remote.

    If you miss the auto-migration, choose import PRemoteM db and select the PRemoteM database file PRemoteM.db. It is in %AppData%\PRemoteM\, or next to PRemoteM.exe if you ran PRemoteM in portable mode. Turn off the RSA encryption of the database in PRemoteM first. Otherwise the names, addresses and passwords are imported unreadable, because 1Remote can not decrypt such a database (support for it was removed in 1Remote 1.3.0).

    Importing from RDP Files

    Warning

    An .rdp file does not contain the password. 1Remote reads the user name and password that mstsc saved in Windows Credential Manager for that address; if there is none, enter the password yourself after the import.

    1. In mstsc.exe, click "Show Options" to expand the window, click the Save As... button under "Connection settings", and save as an RDP file.
    2. In 1Remote, click the + button in the upper-right corner of the main window, and choose "import *.rdp". Select the RDP file you just saved in the pop-up dialog, and click "Open" to complete the import.

    Starting Remote Connections

    Starting from the main window

    1. Double-click a server to open the corresponding remote session.
    2. Or tick the servers and click the Connect button at the bottom of the main window to start several sessions at once.
    3. If you have tagged the servers, you can right-click the tag in the tag bar above the main window, and click the Connect button to start all servers of that tag at once.

    Starting from the Launcher

    Press the default shortcut Alt + M to show the launcher, type a few letters of the server you want, and press Enter to start.

    For more details about the Launcher, please see the Launcher.

    Session view

    Remote sessions open as tabs of a session window. Every tab has a header with the session name; right-click the header to Reconnect or Close the session, to edit or duplicate the server, to copy its address or credentials, or to open an SFTP session to the same server (SSH only).

    • Move a session to its own window: drag the tab out of the window. Drag it back into another session window to dock it there; an empty session window closes by itself.
    • Always open in a new window: tick Always open in new window in the server editor to give this server its own window every time.
    • Keyboard: Ctrl+1 to Ctrl+9 switch between the tabs, F11 toggles a borderless full-screen window, a middle-click on a tab header closes it.
    • Reconnect: when an RDP session loses its connection, 1Remote tries to reconnect up to 5 times and shows Reconnecting...(n/5) in the tab title. If it gives up, the window leaves full screen and offers a Reconnect and a Dismiss button.
    • Window buttons: the title bar of a session window has a pin to keep it always on top, a full-screen button (for RDP and VNC), a red Close all button (when more than one tab is open), and the usual minimize, maximize and close buttons. In Options -> General -> Tab you can move the close button to the left side and choose which buttons the tab headers show.

    Tag management

    Every server can have several tags. All tags are shown on the Tags page of the main window.

    Tags you pin (right-click a tag, Pin) stay in the tag bar above the server list, so one click filters the list.

    Tip

    Keep tag names short, they share the space in the tag bar.

    Rename tag

    Right-click on a tag to find the Rename button.

    Filter by several tags

    Click a tag on a server line to show only the servers with that tag. Hold Ctrl and click more tags to show servers with any of them; hold Alt and click a tag to hide the servers with it. In the tag bar, a click sets the filter and Ctrl + click adds a tag.

    For example: show all servers tagged home, but leave out the ones tagged RDP.

    Launcher ↵

    Launcher

    The launcher is a small window in which you start a remote session with a few keystrokes. Open it with the default shortcut Alt + M.

    Note

    Launcher will be shown on the screen where your mouse is.

    Select

    In the launcher, the servers are ordered by recent use. Use the Up and Down arrow keys to select the desired server, or type some keywords to search for it.

    Press Enter or double-click a server to start the remote session.

    The keyword is matched against the server name and, when Show credentials info is on (see below), also against its address line (address:port). Type #tag to list only the servers with that tag, and -#tag to leave them out.

    Several matching methods are switched on in Options -> Launcher -> Keyword-Matchers, for example Direct match (the keyword appears as typed), Discrete match (the keyword letters appear in this order with gaps), Initials match (db1 finds data-base-server-1) and Chinese PinYin. An exact name match is listed first.

    Action list

    When you select a server, press the Right arrow key to open its action list: connect, connect with another credential, edit, copy the address and so on. Press Left to close the list.

    Show note

    In the server list, press Left to show or hide the note of the selected server.

    Or simply click the note icon.

    Settings

    Options -> Launcher has the settings of the launcher:

    • Enable the launcher and Hot key: turn the launcher off or change the Alt + M shortcut.
    • Keyword-Matchers: the matching methods described above.
    • Show credentials info: show the address line (address:port) under each server in the list, and search it too.
    • Quick Connect: see Quick connect.

    Quick connect

    In the launcher you can connect to a server without creating a server entry for it.

    After the launcher shows up, press the Tab key to switch to the quick connect mode.

    In this view you can select the protocol and type the address and the port, then start the remote session.

    Once you press Enter key, a password window shows up. Fill in the user name and the password (or pick a private key for SSH and SFTP) to continue.

    History

    1Remote remembers the addresses you connected to. They are listed below the input box; click one to fill it in, or click the x at its right end to remove it from the list.

    • What is remembered is controlled by Options -> Launcher -> Allow Quick Connect to save entered address information. It is on by default. When you turn it off, the history is deleted.
    • The list keeps the newest 50 addresses. It is stored on this PC only, in the file .connection_records.json of the .locality folder (see Where your data is).
    • The password is not saved unless you tick Remember the information above in the password window. Tick it and the user name and password are stored together with the address, with the same obfuscation that the database uses for passwords (see Security). Leave it unticked and you type the password every time.

    Warning

    A remembered password can be read by anyone who can read the files of your Windows account. Lock Windows when you leave your computer.

    Alternative credentials

    A server entry holds one address, one port and one set of login data. Alternative credentials add more of them to the same entry: another address, another account or both. You pick one by hand when you connect, or let 1Remote take the first address that answers. This spares you a second entry for the same machine.

    Two typical cases:

    • You connect to a server with a normal account most of the time, and with the root account for maintenance work.
    • You reach your NAS by its LAN address at home and by its WAN address from outside.

    Add an alternative credential

    1. Open the server with Edit. The section Alternative sits under the protocol settings; it says support multi-address multi-account.
    2. Click + under the list. A dialog opens.
    3. Name is required. It is what you pick from later, for example root or WAN. Every other field may stay empty; an empty field takes the value of the server entry (the dialog says Leave blank to inherit the default value).
    4. Fill in what is different: Hostname and Port for another address, User and Password for another account. For SSH, SFTP and the like, tick Use private key to enter a key file instead of a password.
    5. Click Save. The credential shows up in the list; Edit and Delete are next to it.

    The section exists for RDP, RemoteApp, SSH, SFTP, FTP, VNC and Telnet entries. An APP entry (a program started by 1Remote, see APP) gets it as soon as one of its arguments uses the connection macros.

    Connect with one of them

    • In the main window: right-click the server and choose Connect (with alternative `root`). There is one such line per alternative credential.
    • In the launcher: select the server and press Right to open the action list; the same lines are in it. Left closes the list.
    • A double-click still connects with the default data.

    When the credential you pick has its own address, 1Remote connects to that address, whether automatic switching is on or not.

    Automatic address switching

    Tick Automatic address switching under the list; the box is enabled as soon as one alternative credential exists. From then on 1Remote tries the alternative addresses when the default address does not answer, and uses the first one that answers. You no longer switch between LAN and WAN by hand.

    What happens when you connect:

    1. 1Remote tries to open a TCP connection to the default address for 0.1 seconds. When it answers, the session starts at once; nothing else is shown.
    2. Otherwise the window <server>: Availability detection opens with one line per address and a countdown of 5 seconds. A line turns green (with the time it took) when the address answers, red when the connection is refused, and pale grey when there is no answer in time.
    3. The first address that answers wins: the window closes and the session starts with it.
    4. When no address answers within 5 seconds, the window shows We are not able to connect to `<server>`! and no session starts.

    The two buttons in the title bar of the window:

    • _: hide the window and let the test go on in the background. The session starts when an address answers.
    • ✕ (red): stop the test and do not connect.

    Note

    The test is a plain TCP connection to the address and port of the entry. A server that silently drops packets counts as "no answer", so you wait the full 5 seconds; a server that refuses the connection is reported at once.

    Check the address before connecting

    The option Availability detection -> Check if address is available before connect sits under Hostname and Port of every server. It runs the steps above before every connection, with the default address alone (and the alternative addresses when automatic switching is on): when no address answers within 5 seconds, you get the message above instead of a session that hangs until the protocol gives up. RDP entries that use a Remote Desktop Gateway never run the check, because their address is reached through the gateway.

    Database & Security ↵

    A chain is only as strong as its weakest link.

    Security

    1Remote does not have an activation password: it runs in the background and starts sessions from the launcher (Alt + M), and that only works well if nothing asks for a password every time (the reasons are at the end of this page). What it does instead, and what you should do yourself, is listed on this page.

    What 1Remote does for your passwords

    Obfuscation in the database

    Passwords, private key paths and so on are not stored as plain text in the database, but they are only obfuscated: the key used for that is the same in every copy of 1Remote, it is not tied to your Windows account or to a password of yours. Somebody who gets hold of your database file (or of a json export, which is plain text anyway) can therefore read the passwords with a little work.

    So the real protection is the protection of the files:

    • Turn on hard disk encryption such as BitLocker, so a stolen disk does not hand out your servers.
    • Lock Windows when you leave the computer.
    • When you share a database with a team, do it with database permissions: a read-only account can connect to the servers but can not edit, delete or copy the credentials from inside 1Remote (see Team sharing). Remember that such an account can still read the database itself.

    Secondary verification

    You can make 1Remote ask for proof that it is really you before it shows a password. Turn it on in Options -> General -> Security -> Windows credentials verification is required to view passwords. It is off by default.

    When it is on, 1Remote asks you to verify before:

    • a password is shown in clear (the eye button next to a password field),
    • a password is copied to the clipboard (Copy password to clipboard in the server menu),
    • servers are exported to a json file.

    The verification uses Windows Hello (fingerprint, face or PIN) when your PC has it set up, otherwise the Windows credential dialog asks for your Windows user name and password. Turning the option off asks for the verification first, so nobody can switch it off without passing it.

    Note

    The verification only guards the ways to look at a password listed above. Connecting to a server never asks for it, and the verification does not change how the passwords are stored.

    Credentials Vault

    The Credentials Vault (its own page in Options) is a list of named accounts, each with a user name and a password or a private key. Every database you use (every data source, see Use online database) has its own list. In the server editor, click the Credentials Vault button and pick an entry instead of typing the account: the server then refers to that entry.

    Change the password of the entry once, and every server that refers to it uses the new password from the next connection on. That is the point of the vault: when a password changes, you fix it in one place instead of server by server.

    Why 1Remote does not have an activation password

    1Remote runs in the background and starts a session from the launcher (Alt + M). If you had to enter a password every time you open the launcher, the launcher would lose its point. And a password that is only asked once, at start, protects little. So we leave the protection to the system, to security software and to your habits: lock the computer when you leave it, and 1Remote needs no activation password. A user who does not lock the computer would not be safe with an activation password either, because the passwords can leak in other ways.

    Summary

    • Lock Windows when you leave your computer.
    • Enable hard disk encryption such as BitLocker.
    • Turn on the secondary verification if other people use your Windows account.
    • Back up your data frequently.

    You can manage your servers on several devices, and keep the same server list on all of them. This page shows where 1Remote keeps its data and the three ways to share it: a json export, a synced SQLite file, or an online database.

    Where your data is

    1Remote keeps its data in one of two places, depending on the mode you chose on the first start (see Run it):

    What Portable mode (data in the program folder) AppData mode
    Settings <program folder>\1Remote.json %AppData%\1Remote\1Remote.json
    List of data sources <program folder>\1Remote.dataSources.json %AppData%\1Remote\1Remote.dataSources.json
    The default database Local (SQLite) <program folder>\1Remote.db %AppData%\1Remote\1Remote.db
    Local data: window positions, icons, logs, Quick Connect history <program folder>\.locality\ %LocalAppData%\1Remote\.locality\

    In portable mode the whole program folder is your data: copy it and you have everything. In AppData mode you only need the two .json files and the .db file to move your servers to another PC.

    By export

    1. Select the servers you want, click Export at the bottom of the main window and save the json file.
    2. Copy the file to the other device.
    3. On the other device click + -> Import -> import json.

    Warning

    The json file contains all passwords in plain text.

    By a synced SQLite file

    • Our main database is a SQLite database that does not lock the file, so you can copy it while 1Remote is running.
    • Every 10 seconds 1Remote checks whether the database file was changed by someone else (it compares a change timestamp inside the database). If so, it reloads the servers.

    This means you can put the database file in a folder that a sync tool keeps up to date on all your devices, and 1Remote picks up the changes by itself.

    Tip

    In Options -> Database -> Local -> Edit, you can see where your database file is.

    You can also change the db path there, for example to move it into the synced folder.

    Sync tools that work for this:

    • Synology Drive (Synology NAS)
    • Google Drive
    • OneDrive
    • Jianguoyun (坚果云)

    Warning

    Do not remove the database file while 1Remote is running, and do not edit on two devices at the same time: 1Remote does not lock the data while you edit, so the second device may overwrite what the first one changed.

    By using MySQL or PostgreSQL

    An online database is the most robust way to synchronize data. When server info is edited on one device, other devices see the change within about 10 seconds, because they use the same 10-second check. Go to Options -> Database -> Add and choose MySQL or PostgreSQL to set it up, check Online database for more details.

    Warning

    1Remote does not use concurrency locks on data editing, so if you modify the database on two devices at the same time, data loss may occur. Please try to avoid this situation.

    Use online database

    Besides the local SQLite database Local, 1Remote can keep servers in a MySQL or a PostgreSQL database. You can connect to several databases at the same time, and every server belongs to one of them.

    This is where more than one database becomes useful:

    • At home: connect to the PostgreSQL database on your NAS to manage your personal servers.
    • At work: connect to the database on your home NAS and to the MySQL database on the company server, so you can reach your private servers and the servers for work in one list.
    • For a team: all colleagues connect to the same database. Those with a read-only account can see and connect to the servers but can not change them, see Team sharing.

    Add a database

    1. Click Options in the main window and open the Database page.

    2. Click Add and choose MySQL or PostgreSQL.

    3. Fill in the form and click Test connection: a message box tells you whether the account can reach the database.

    4. Click Save.
    Field What to enter
    Data Source name The name 1Remote shows for this database, for example Home NAS. Any name is fine.
    Hostname The address of the database server, for example 192.168.1.10 or nas.local.
    Port 3306 for MySQL, 5432 for PostgreSQL. Both are filled in for you.
    Database The name of an existing database on the server, 1Remote is filled in as a suggestion. 1Remote creates its tables in it on the first connection; the database itself has to exist.
    User, Password An account of the database server. See Permissions for what the account must be allowed to do.

    1Remote creates three tables in the database by itself: Configs, Servers and Credentials (the Credentials Vault). You only have to create the database; the tables are made during the first connection with a read-and-write account.

    The database list

    After Save the database shows up in the list on the Database page, with an icon that shows its state:

    Icon Meaning
    red icon 1Remote can not connect, for example a wrong password or the server is unreachable. Move the mouse over the icon to see the reason, click it to try again.
    green icon Connected, and the account may read and write.
    green icon with lock Connected, but the account may only read. The name gets the addition (Readonly), see Permissions.

    Note

    The screenshots on this page are from an older version of 1Remote; the names of the fields and buttons are still the same.

    Choose the database of a new server

    When more than one database is connected, 1Remote asks Please select a Data Source when you add a server. Read-only databases are in the list too, but their Select button stays disabled: a new server needs a database you may write to.

    In the List view the servers are grouped by database, so you can see at a glance where a server is stored:

    Changes show up within about 10 seconds

    Every 10 seconds 1Remote asks each connected database whether something changed, and reloads the servers of that database if so. When a colleague adds a server, it shows up on your screen within about 10 seconds without doing anything. The same check is used for the local SQLite file, see Data synchronization.

    Permissions

    What an account can do inside 1Remote follows what the account may do in the database:

    • Read and write account: can do everything. The first connection to a new database must be made with such an account, because 1Remote creates its tables then. The account needs Create, Select, Insert, Update and Delete on the database.
    • Read-only account (Select only): inside 1Remote it can see the servers and connect to them, nothing more. For servers in such a database the menu of a server offers no Edit, Duplicate, Delete, Copy username to clipboard or Copy password to clipboard, the Edit and Delete buttons at the bottom of the main window stay disabled, and the database carries the addition (Readonly) in the database list.

    1Remote finds out which kind of account it is on every connection: it tries to delete, insert and update a test entry (permission_check) in the Configs table. If one of these fails, the database is treated as read-only.

    Warning

    Read-only is not a password protection. A read-only account can still read the whole Servers table, and the passwords in it are only obfuscated, not encrypted (see Security). Hand out the read-only account only to people who may see those passwords.

    1Remote does not lock the data while you edit it: if two people change the same server at the same time, the last one to save wins. Keep the number of read-and-write accounts small.

    Protocol ↵

    Especial ↵

    APP: start any program

    The APP protocol starts a program on your own PC with the arguments you choose, for example a browser with a URL, cmake-gui with a build folder or NoMachine with a session file. Such an entry shows up in the server list and the launcher like any other server, so you can start the program with a few keystrokes. Its arguments can use the address, the user name and the password of the entry, which makes the entry a launcher for programs that 1Remote does not know.

    Add an APP entry

    1. Click the + button in the upper-right corner of the main window and choose APP.
    2. Exe path: type the path of the program or click Select. Environment variables are allowed, for example %VNC%\viewer.exe.
    3. If the name of the exe is known to 1Remote, it fills in the arguments, the hosting switch and the protocol name for you (see Presets). You get a question whether to replace the current parameter list when the entry already has arguments.
    4. Hosting: tick it to show the program inside an 1Remote tab. Some programs do not allow that, so untick it when the program does not start.
    5. Protocol (optional): the name shown instead of APP in the server list, for example NoMachine.
    6. Fill in the Cmd parameter list, see the next section.

    The parameter list

    Instead of one long command line, the arguments of an APP entry are a list. Each line of the list is one argument with a Name, a Prefix (the switch in front of the value, may be empty), a Value and a Preview of what ends up on the command line. Use Edit to open the editor, + to add an argument, and the buttons next to an argument to move it up or down, change it or delete it. The Preview line under the list shows the complete command line; Test starts the program with it right away.

    The editor of one argument has these fields:

    Field Meaning
    Type Normal: text. Int/Float: a number, checked when you save. File: a path, with a Select button, must exist. Secret: a password, stored obfuscated like other passwords and shown as ******. Flag: the prefix alone, when the value is 1. Selection: one of the lines in Selections. Const: fixed text, usually a macro like %1RM_HOSTNAME%; in the list it is plain text that you change with the Edit button.
    Name A name for the argument, shown in the list. Must be unique in the entry.
    Prefix The text in front of the value, for example -P. Untick append blank after prefix when the value must follow directly, as in -P22 or sftp://.
    Value The value. Macros and environment variables are allowed.
    append blank after value Add a space behind the value. Untick it when the next argument must follow directly, as in user:password@host.
    Nullable The argument may be empty; an empty argument is left out of the command line.
    Description Shown as a hint in the list.

    RDP in mstsc.exe mode

    Normally 1Remote shows an RDP session inside its own window, using the Remote Desktop ActiveX control of Windows. In mstsc.exe mode it writes a temporary .rdp file instead and starts the session with mstsc.exe <file>.rdp. mstsc.exe is the Remote Desktop Connection program of Windows, so the session then opens in a window of its own, and you can put any setting into the .rdp file that mstsc.exe understands.

    When to use it

    • Your PC has two or more monitors with different scale factors (for example 100 % and 150 %), and you want the session on all screens. The ActiveX control can not handle mixed scale factors; mstsc.exe can. 1Remote switches to mstsc.exe mode by itself in this case, you do not have to do anything.
    • You need a setting that the ActiveX control does not offer, for example the choice of the monitors (selectedmonitors), or the resolution of the session (desktopwidth, desktopheight).

    Turn it on

    Open the RDP server with Edit and tick Enabled under mstsc.exe mode. The session then always starts with mstsc.exe, whatever your monitors are.

    Additional settings

    The text box Additional settings holds the lines to add to the .rdp file, one setting per line in the usual .rdp form name:type:value. Leave it empty to get the same session as the built-in runner.

    Setting Effect
    selectedmonitors:s:0,2 Use only the monitors number 0 and 2 for the remote desktop; monitor number 1 keeps showing your local desktop. Click Check monitor number to see which number each monitor has (it runs mstsc /l).
    redirectcomports:i:1 Redirect the COM ports of your PC to the session.
    desktopwidth:i:800 Width of the remote session in pixels.
    desktopheight:i:600 Height of the remote session in pixels.

    SSH tunnel

    An SSH tunnel forwards a port of your PC through the SSH server to another host, so you can reach that host as if it were on your own network. Example: a web interface on 192.168.1.2:80 that only the SSH server can reach becomes available as http://localhost:777 on your PC.

    The built-in SSH runner of 1Remote is PuTTY, and PuTTY can open such tunnels. 1Remote creates the PuTTY session for every server by itself, so you can not set the tunnel in PuTTY's own window. Instead you put the tunnel into a session file and name that file in the server entry: PuTTY session file.

    The session file

    The session file is a text file in the format KiTTY (a PuTTY variant) uses to save sessions: one setting per line, written as Setting\Value\. For a tunnel you only need the setting PortForwardings. Save this as tunnel-777.txt, for example with Notepad:

    PortForwardings\L777=192.168.1.2:80\

    Read L777=192.168.1.2:80 as: listen on local port 777 and forward it to 192.168.1.2:80. Several forwardings are separated by commas:

    Entry Meaning
    L777=192.168.1.2:80 Local forwarding: localhost:777 on your PC leads to 192.168.1.2:80.
    D1080 Dynamic forwarding (SOCKS proxy): programs that use localhost:1080 as proxy go through the SSH server.
    R8080=localhost:80 Remote forwarding: port 8080 on the SSH server leads to port 80 of your PC.

    A full line with three forwardings:

    PortForwardings\L777=192.168.1.2:80,D1080,R8080=localhost:80\

    Note

    The backslashes matter: one after the setting name and one at the end of the line. If the file does not follow this format, 1Remote answers Invalid KiTTY session config file. when you select it.

    Set it up

    1. Open the SSH server with Edit.
    2. Make sure Selected runner is still Follow the global settings or Built-in PuTTY; the field PuTTY session file is only shown for the built-in runner.
    3. Click Select next to PuTTY session file and pick the text file.
    4. Click Save and connect. The tunnel is open as long as the session is open; open http://localhost:777 in a browser to use it.

    Every other setting of the file is applied to the session too (colours, key bindings, bell, and so on), with one exception: the address, the port, the user name and the private key always come from the server entry in 1Remote, never from the file.

    Get such a file from KiTTY

    You do not need KiTTY to write the file, but it helps when you want more than the tunnel. KiTTY is a PuTTY variant that can save a session into a file:

    1. Download KiTTY portable and start it.
    2. Type a name under Host Name (or IP address) and Saved Sessions, and click Save. The host name does not matter, 1Remote replaces it.
    3. Click Connection -> SSH -> Tunnels, enter Source port 777 and Destination 192.168.1.2:80, click Add, and click Save again on the Session page.
    4. KiTTY now has a file with the name of the session in its Sessions folder (in the portable version: kitty\…\data\config\Sessions\). That is the file to pick in step 3 above.

    Why

    Suppose you are the team leader and your company has several servers to manage: the AI servers are for the AI team, the web servers are for the web team.

    A typical use case is:

    • Only you and your boss may add and modify servers. The other colleagues can only see the servers in the list; they can not edit them or see the password.
    • The AI team works with the AI servers, the web team with the web servers.

    1Remote can help you manage these servers with the Team sharing feature: the team connects to the same database with two kinds of account.

    Account Connect View address Edit Delete View password
    Read-only account (Select only) ✅ ✅ ❌ ❌ ❌
    Read-and-write account ✅ ✅ ✅ ✅ ✅

    Your team members connect to the same database with a read-only account: they can only see the servers and connect to them.

    You connect with the read-and-write account and can add, edit and delete servers.

    The Team sharing feature offers only very basic access control, and is not designed to give each team member an individual set of servers. "View password" means inside 1Remote only, see the warning below. To keep the servers of two teams apart, use two databases.

    How

    1. Create two accounts in MySQL or PostgreSQL with different permissions:

      In database test, account writable may select, insert, update and delete data, while account readonly may only select data. 1Remote treats an account as read-only unless all three of delete, insert and update work (see Permissions).

    3. Your team members connect to the test database with account readonly. They will not be able to edit the servers, but they can view the servers and connect to them.

      The database carries the addition (Readonly) in the list of Options -> Database:

      The server menu of a team member has no Edit, Duplicate or Delete entries:

    4. Once you edit the servers, the team members will see the changes within about 10 seconds.

    Streamline by pre/post connect script ↵

    Scripts before connect and after disconnect

    For every server you can set two scripts: one that runs before 1Remote connects, and one that runs after the session was disconnected. A script is a .bat or .cmd file, a .ps1 PowerShell script or a .py Python script. The usual case is to open a VPN before the connection and to close it after the session, see Open a VPN before connect.

    Set up the scripts

    1. Open the server in the editor (Edit).
    2. In Script before connect type the path of the script, or click Select to pick the file. Arguments may follow the path, for example D:\scripts\before.ps1 -Vpn home.

    3. Click Test: 1Remote tells you what it is going to run, runs the script and shows its exit code.

    4. Do the same for Script after disconnected.

    5. Click Save. From now on the scripts run every time you connect to this server.

    How the scripts are run

    • The working directory of a script is the folder the script file is in.
    • A .ps1 file is started with powershell.exe -File, a .py file with python (so Python has to be in the PATH), a .bat or .cmd file directly.
    • Script before connect: 1Remote waits until the script has ended. Exit code 0 means "go on and connect"; any other code stops with the message Script ExitCode = <code>, connection abort!. Tick Hide script window(not recommended for script take long time) to run the script without a window; the tooltip warns you because you would not see a script that hangs. The Test run always shows the window.
    • Script after disconnected: runs when the session ends, that is when you close its tab (or, for a program that runs unhosted in its own window, when that program has exited). 1Remote does not wait for it and ignores its exit code. Its window is hidden; only the Test run shows it.

    Tip

    If Windows refuses to run your .ps1 file with a message about the execution policy, run this once in a PowerShell window:

    Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

    Environment variables

    Every script gets these variables, so it knows which server and which session it is about:

    Variable Content Example
    SESSION_ID A number that identifies the session. It is the same in the before and the after script of one session, and different in the next session. 16312252
    SERVER_ID The internal id of the server. It stays the same when the server is renamed. 01GWJXAXUOBERQPARPSGKYKWBWQ
    SERVER_NAME The name of the server as shown in the list. NAS
    SERVER_HOST Address and port of the server, separated by a colon. 192.168.0.130:22
    SERVER_TAGS The tags of the server, separated by commas. home,nas

    In PowerShell you read them as $env:SERVER_NAME, in a batch file as %SERVER_NAME%.

    Example script

    The following PowerShell script shows all variables, writes them to a file and ends with exit code 0, so the connection goes on:

    $sessionID  = $env:SESSION_ID
$serverID   = $env:SERVER_ID
$serverName = $env:SERVER_NAME
$serverHost = $env:SERVER_HOST
$serverTags = $env:SERVER_TAGS

Write-Host "SESSION_ID: $sessionID"
Write-Host "SERVER_ID: $serverID"
Write-Host "SERVER_NAME: $serverName"
Write-Host "SERVER_HOST: $serverHost"
Write-Host "SERVER_TAGS: $serverTags"

    Open a VPN before connect

    Some servers can only be reached through a VPN. Then you have to open the tunnel first, wait until it is up, and only then start the remote session. 1Remote can do the waiting for you: open the VPN in Script before connect and close it in Script after disconnected.

    The example uses OpenVPN (its program is called openvpn-gui). The idea works with any VPN that can be started from a command line.

    The script before connect: open the VPN and wait

    open_vpn.ps1:

    # SERVER_HOST looks like "192.168.50.10:3389"
$address, $port = $env:SERVER_HOST.Split(':')

# tells the running openvpn-gui to connect the config "myconnection.ovpn"
& "C:\Program Files\OpenVPN\bin\openvpn-gui.exe" --command connect myconnection.ovpn

function Test-Port($hostname, $port, $timeoutMs = 2000) {
    $client = New-Object System.Net.Sockets.TcpClient
    try {
        $result = $client.BeginConnect($hostname, $port, $null, $null)
        if ($result.AsyncWaitHandle.WaitOne($timeoutMs)) { return $client.Connected }
        return $false
    } catch { return $false } finally { $client.Close() }
}

Write-Host "Waiting for the VPN..." -NoNewLine
$i = 0
while (-not (Test-Port $address $port)) {
    if ($i++ -ge 60) {
        Write-Error "The server $address is still not reachable after 60 tries."
        exit 1   # any code other than 0 stops the connection
    }
    Write-Host -NoNewLine ' .'
    Start-Sleep -Seconds 1
}
Write-Host ""
Write-Host "The VPN is up, connecting to $address"
exit 0

    What it does:

    1. It reads the address and the port of the server from SERVER_HOST, one of the variables every script gets. So the same script works for every server.
    2. It asks the running openvpn-gui to connect myconnection.ovpn. Replace the name with your config file; the .ovpn file is enough, openvpn-gui finds it in its config folder. The command only talks to openvpn-gui, so openvpn-gui has to run (it starts automatically with Windows when OpenVPN was installed with that option).
    3. It tries to reach the server port up to 60 times, each try waits up to 2 seconds and is followed by a pause of 1 second, so it gives up after about 3 minutes at most. As soon as the server answers, the script ends with exit code 0 and 1Remote connects. After 60 tries it ends with exit code 1, and 1Remote shows Script ExitCode = 1, connection abort! instead of connecting.

    The script after disconnected: close the VPN

    close_vpn.ps1:

    & "C:\Program Files\OpenVPN\bin\openvpn-gui.exe" --command disconnect myconnection.ovpn

    Set it up

    1. Save both scripts, for example in D:\scripts\.
    2. Open the server with Edit, pick open_vpn.ps1 as Script before connect and close_vpn.ps1 as Script after disconnected (click Select).
    3. Click Test next to the first script: 1Remote tells you what it will run, runs the script (its window shows a dot for every try) and then shows The exit code of the script = 0 when the server answered.
    4. Leave Hide script window unticked for this script: it waits for the VPN, and with a hidden window you can not see whether the VPN is still coming up or the script hangs.
    5. Click Save.

    Note

    If other people use the same server from the shared database, the scripts run for them too, and fail when they do not have D:\scripts\open_vpn.ps1. Put the scripts on all those PCs, or keep the server in a database only you use.

    Command line

    1Remote.exe accepts a few arguments. You can use them in a shortcut, in a script or in the Run box (Win + R), for example to start a remote session with one double-click.

    Note

    If 1Remote is already running, a second start does not open a second copy: the arguments are handed over to the running copy and the new process closes at once. So 1Remote.exe "My Server" connects from the running 1Remote, and starts 1Remote first when it is not running.

    One dash or two makes no difference: --install and -install are the same argument.

    Start a connection

    Argument What it does
    "<server name>" Connects to the server with exactly this name; upper and lower case does not matter. Put the name in quotes when it contains spaces. If several servers have this name, all of them are started.
    ULID:<server id> Connects to the server with this id. The id is a ULID (Universally Unique Lexicographically Sortable Identifier) that stays the same when the server is renamed, so 1Remote uses it in the desktop shortcuts it creates. It is the same value a script gets as SERVER_ID.
    #<tag> Connects to all servers with this tag, for example #work.

    Several arguments start several sessions at once:

    1Remote.exe "My Server" #work

    Add --start-minimized to keep the main window closed and only open the sessions:

    1Remote.exe "My Server" --start-minimized

    An argument that matches no server (a typo, for example) is ignored; 1Remote does not show a message for it.

    Tip

    You do not know the id of a server? Right-click a desktop shortcut that 1Remote created for it, choose Properties and read the Target field: the part after ULID: is the id.

    Change a setting

    Argument What it does
    --install-desktop-shortcut Creates the shortcut 1Remote.lnk on your desktop. An existing one is replaced.
    --uninstall-desktop-shortcut Deletes that shortcut.
    --install-startup Turns on Run automatically at OS startup(minimized) (the same as the option in Options -> General -> Startup).
    --uninstall-startup Turns it off.
    --install Same as --install-desktop-shortcut --install-startup.
    --uninstall Same as --uninstall-desktop-shortcut --uninstall-startup.

    When 1Remote is not running and you pass only arguments from this table, it changes the setting and closes without opening its window.

    Start without a window

    Argument What it does
    --start-minimized Starts 1Remote in the background: the main window stays closed, only the tray icon shows. The launcher (Alt + M) works as usual. Double-click the tray icon to open the main window.

    Without arguments, 1Remote starts with its main window, or brings the window of the running copy to the front.

    Desktop shortcut for connections

    A shortcut on your desktop can start one server, several servers at once, or all servers of a tag with a double-click. 1Remote creates these shortcuts for you; they use the command line arguments, so you do not have to type anything.

    One server

    Right-click the server, or click the Settings button that appears when you move the mouse over it, and choose Create desktop shortcut.

    Several servers at once

    1. Tick the check boxes of the servers, or hold Ctrl / Shift and click them.
    2. Click Create desktop shortcut at the bottom of the main window.

    The shortcut starts all of them. Its name is the names of the servers joined with &.

    All servers of a tag

    Right-click a tag in the tag bar above the server list and choose Create desktop shortcut.

    The shortcut is named Tag=<tag>. It always starts the servers that have the tag when you double-click it, so servers you tag later are started too.

    What such a shortcut does

    • Double-click it and 1Remote starts (when it is not running yet) and connects to the servers. The main window stays closed; the sessions open in a session window.
    • It refers to the servers by their internal id, not by name, so it keeps working when you rename a server. If the server was deleted, or you copy the shortcut to a PC whose 1Remote does not know that server, nothing happens.
    • It contains no password. It only works together with your 1Remote data, so you do not hand out credentials when you pass it on.
    • Its icon is the icon of the server. For several servers the icons are combined into one.

    Help translation

    It would be really awesome to offer 1Remote in many different languages! So you're really welcome to translate 1Remote into your (native) language, or to fix a mistake in an existing translation. This page explains how the translation files work, how to send us a change, and who has helped so far.

    1Remote currently ships 16 languages: English, 简体中文, 正體中文, čeština, Deutsch, Español (Argentina), Français, Galego, Italiano, 日本語, 한국어, Polski, Portuguese (pt-BR), Português (pt-PT), Русский and Türkçe. The 16 come from the 16 CSV files in Ui/Resources/Languages/glossary/; each one is listed with its contributor below.

    How the translation files work

    All user-visible text lives in CSV files in the folder Ui/Resources/Languages/glossary/ of the source repository, one file per language: en-us.csv (English), zh-cn.csv (Simplified Chinese), de-de.csv (German) and so on. English is the template: every other language file has the same rows in the same order.

    Each file looks like this:

    key;en-us
language_code-ISO;en-US
language_code-google;en
language_name;English (en-US)
Warning;Warning
Error;Error
...
    • The first column (key) identifies a text. Never change it.
    • The second column is the text shown in the app. This is what you translate.
    • The first 4 rows describe the language itself (its file code, its ISO code such as ko-KR, its Google Translate code, and the name shown in the language list).

    The *.xaml files and LanguagesList.cs in the folder Ui/Resources/Languages/ are generated from the CSV files by a script. Do not edit them by hand.

    CSV rules

    • The delimiter is a semicolon ; and the file must be saved with UTF-8 encoding and LF line endings.
    • Do not open the file with Office Excel: it changes the encoding. Use a code editor (VS Code, Notepad++) or a web editor such as https://edit-csv.net.
    • To put a semicolon or a line break inside a text, enclose the whole text in double quotation marks. To put a double quotation mark inside the text, write it twice ("").
    • A row with an empty second column falls back to Google Translate when the script runs (the result is cached in glossary_translated_by_google/). If you are unsure about a term, leave it empty rather than guessing.

    Fix or improve an existing translation

    1. Fork and clone the repository.
    2. Open the CSV file of your language in Ui/Resources/Languages/glossary/ and edit the second column of the rows you want to change.
    3. Regenerate the resource files: run conver_glossary_to_xaml.bat in Ui/Resources/Languages/ (it needs Python; the first run installs a few packages and may fail, run it again). It updates the .xaml file of your language.
    4. Commit the CSV file and the regenerated .xaml file, then open a pull request.
    5. Add your name to the Current contributors list below. Click the pencil icon at the top of this page to edit the page on GitHub.

    Add a new language

    1. Fork and clone the repository.
    2. Copy glossary/en-us.csv and rename the copy with your language code, for example es-es.csv for Spanish or ko-kr.csv for Korean.

    3. Edit the first 4 rows of the new file:

      Row Column 2 Example Meaning
      1 en-us es-es File name / internal code
      2 en-US es-ES ISO language code
      3 en es Google Translate code
      4 English (en-US) Español (es-ES) Name shown in the app's language list

    4. Translate the second column of all the other rows.

    5. Run conver_glossary_to_xaml.bat in Ui/Resources/Languages/. It creates the .xaml file of your language and adds the language to LanguagesList.cs.
    6. Commit the CSV file, the new .xaml file and LanguagesList.cs, then open a pull request.
    7. Add your name to the Current contributors list below (see step 5 of the previous section).

    Tip

    If the script cannot reach Google Translate from your network, open glossary_maker.py (the Python script that conver_glossary_to_xaml.bat runs) and adjust the proxy settings of the Translator(...) line, as described in readme.md.

    Stable build: which package should I download?

    Every stable release offers six zip packages: one for each of .NET 9, .NET 10 and .NET 11, in two variants each.

    Variant (part of the file name) Size What your PC needs
    .recommended.zip and the other packages without self-contained about 20 MB The .NET Desktop Runtime of the same version as the package: a -net10- package needs .NET 10, a -net9- package needs .NET 9 and a -net11- package needs .NET 11. A newer runtime is not enough.
    self-contained about 90 MB Nothing. The runtime is inside the package.

    If you are not sure which one to take: download the .recommended.zip package (it is the .NET 10 one) and install the .NET 10 Desktop Runtime, choose Windows Desktop Runtime 10.0 (x64), or run winget install Microsoft.DotNet.DesktopRuntime.10.

    Run it

    1. Unpack the zip into a folder your user account may write to, for example D:\Tools\1Remote, and start 1Remote.exe. There is no installer.

    2. On the first start the app asks where it should keep your data:

      • Portable mode: settings and the database are stored in the program folder (1Remote.json, 1Remote.db), so you can copy the whole folder to another PC or a USB drive.
      • AppData: settings and the database are stored in %AppData%\1Remote.

      To switch the mode later, rename the marker file in the program folder: FORCE_INTO_PORTABLE_MODE stands for portable mode, FORCE_INTO_APPDATA_MODE for AppData. 3. To upgrade, close the app, unpack the new package into the same folder and overwrite the old files. Your data is kept.
